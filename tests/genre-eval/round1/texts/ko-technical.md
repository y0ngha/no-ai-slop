# 모래함이 업로드 순서와 재시도를 정하는 방법

모래함은 파일 업로드 대기열입니다. 사용자가 고른 파일을 등록하고, 보낼 순서를 정하고, 서버가 저장했는지 확인합니다. 여기서는 화면 표시나 압축 방식보다 전송 순서와 재시도 규칙을 설명합니다. 아래 규칙은 모래함에만 해당하며 다른 업로드 제품도 같다는 뜻은 아닙니다.

## 파일 등록과 전송 순서

추가한 파일은 먼저 `waiting` 상태가 됩니다. 계정마다 기다리는 파일과 전송 중인 파일을 합쳐 최대 20개까지 둘 수 있습니다. 재시도를 기다리는 파일도 포함하지만, 실패해서 멈췄거나 완료된 파일은 세지 않습니다. 이미 20개라면 새 파일을 등록하지 않고 "대기열이 가득 찼습니다"를 표시합니다.

파일 하나의 크기 제한은 50 MiB이며, 1 MiB는 1,048,576바이트입니다. 크기를 넘긴 파일은 등록 전에 거절하므로 전송 시도 횟수도 생기지 않습니다.

전송을 맡는 실행기는 계정마다 최대 2개입니다. 자리가 비면 등록 시간이 빠른 파일부터 가져갑니다. 시간이 같으면 등록 번호가 작은 파일을 먼저 고릅니다. 등록 번호는 새 파일을 등록할 때마다 증가합니다. 전송을 시작한 파일의 상태는 `sending`입니다. 세 번째 파일의 진행률이 0이어도 앞의 두 파일을 보내는 중일 수 있으므로, 진행률만 보고 오류라고 판단하지 않습니다.

## 언제 다시 보내는가

전송을 시작한 뒤 응답 없이 30초가 지나거나 HTTP 503을 받으면 자동으로 재시도합니다. HTTP 201만 성공으로 처리하고 `done`으로 바꿉니다. HTTP 400, 401, 403을 비롯한 나머지 응답 코드는 자동 재시도하지 않고 `failed`로 끝냅니다.

최초 전송을 포함해 한 파일당 최대 3번 시도합니다. 첫 번째 실패 뒤에는 2초, 두 번째 실패 뒤에는 6초를 기다립니다. 세 번째 시도도 실패하면 더 기다리지 않고 끝냅니다. 한 파일이 재시도를 기다리는 동안 다른 파일은 전송할 수 있습니다.

재시도를 기다릴 때는 `retry_wait` 상태입니다. 이 파일은 20개 한도에 포함되지만 실행기 자리를 차지하지는 않습니다. 대기 시간이 지나면 원래 등록 시간과 번호를 유지한 채 `waiting`으로 돌아갑니다. 그래서 새 파일보다 먼저 선택될 수 있지만, 이미 전송 중인 파일을 밀어내지는 않습니다. 2초나 6초가 지나도 실행기 두 개가 모두 바쁘면 더 기다려야 합니다.

## 중복 저장과 취소

파일을 등록할 때 만든 `upload_key`는 자동 재시도에서도 그대로 사용합니다. 서버는 같은 키의 저장 결과를 24시간 보관합니다. 이미 저장한 키로 요청이 오면 새 복사본을 만들지 않고 같은 파일 번호와 HTTP 201을 돌려줍니다.

파일 저장은 성공했지만 브라우저가 응답을 받지 못할 수 있기 때문에 필요한 규칙입니다. 응답만 유실된 경우라면 두 번째 요청으로 첫 번째 저장 결과를 확인할 수 있습니다. 다만 모든 통신 실패가 응답 유실 때문인 것은 아닙니다.

사용자가 취소한 파일은 `cancelled`가 되고 이후 자동 재시도는 없습니다. 취소해도 이미 서버에 저장된 파일까지 지우지는 않습니다. 전송 취소와 서버 파일 삭제는 별도 동작입니다.

모래함의 이 버전은 목록을 메모리에만 보관하므로 브라우저를 새로 고치면 대기열을 복구하지 못합니다. 같은 파일을 다시 등록해도 새 키가 생깁니다. 따라서 새로 고치기 전에 저장한 파일과의 중복 방지는 보장하지 않습니다.

## 문제를 조사할 때 남길 기록

파일명뿐 아니라 등록 번호, 상태, 시도 횟수, 마지막 응답 코드를 함께 남겨 주세요. 특히 "세 번 재시도했다"는 최초 전송 외에 세 번을 더 보냈다는 뜻으로 읽힐 수 있습니다. 모래함 기록에는 "총 3회 시도"라고 적습니다. 현재 상태와 총 시도 횟수를 먼저 확인하면 파일이 기다리는 이유를 파악하기 쉽습니다.
