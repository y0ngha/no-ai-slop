# How the Alder search index refresh works

There are several moving pieces involved in the continued availability of search, and it is useful to have an understanding of those pieces before making changes to the refresh worker. In Alder, the document store is the source of truth and the search index is a separate representation of it. A document being saved successfully does not, by itself, signify that the document is immediately searchable. The point that tends to become relevant during incidents is that an older index can still be served, but only within a specific age limit and with a specific message.

The refresh worker runs every five minutes. It reads a snapshot of published documents and builds a new index generation without modifying the generation currently handling requests. A generation has an identifier such as `gen_204`, a `snapshot_at` timestamp, and a status. Here, `snapshot_at` means the time the document snapshot was taken, not the time the worker finished. A build that takes three minutes therefore starts serving data that is already three minutes old. This distinction is a small detail with a fairly substantial operational implication.

After building, the worker checks three things: the generation can be opened, every indexed document has a document ID, and the document count differs from the previous generation by no more than 15%. A larger difference requires a human review; it is not automatically proof of bad data. If any check fails, the worker leaves the active generation unchanged and records a failed refresh. If all checks pass, it changes the active-generation pointer in one atomic operation. Requests that already hold the old generation may finish against it. New requests use the new pointer.

There is also the matter of the fallback, which deserves to be made explicit. When a refresh fails, search may continue using the active generation only while its age is at most 20 minutes. Age is calculated at request start as `request_started_at - snapshot_at`, using the server clock. At exactly 20 minutes, the generation is still eligible. At 20 minutes and one second, it is not. A successful but slow refresh does not reset this clock, because age still comes from the snapshot timestamp.

If the latest refresh failed and the active generation is eligible, the API returns its ordinary results with `stale: true`. The interface displays the exact notice "Results may be up to 20 minutes old." This applies even if the actual age is only seven minutes. We deliberately use a stable upper-bound message rather than presenting a changing estimate. Empty results from that generation are still valid results; the client must not interpret an empty list as a reason to retry against another generation.

If the active generation is too old, or no active generation exists, the API returns HTTP 503 with code `SEARCH_TEMPORARILY_UNAVAILABLE`. It returns no result items. The interface says "Search is temporarily unavailable. Please try again shortly." There is no fallback to an unrestricted database query. Such a query would have different permission behavior and could also place a large load on the document store. This is why adding one as a quick remedy is not an equivalent implementation of the fallback.

For testing purposes, use a fixed clock and cover both sides of the 20-minute boundary. Also check that a failed count check does not change the active pointer. The generation age and failed-refresh count are recorded separately, which helps avoid a somewhat misleading conclusion: repeated worker failures are concerning, but it is the age rule that determines whether a particular request can receive results. A retry may recover the refresh process; it must never extend the serving deadline of an existing snapshot.
